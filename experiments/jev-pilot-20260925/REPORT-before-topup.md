# Jev 对照试验：本仓库审核说明与代码证据一致性

## 结论

Jev 接口与新增筛查模块真实运行成功。18 条判断与预先固定的 Commander 标签一致 16 条（88.9%）；12 条不应获得支持的主张均未被判为 supported，但两条“证据不足”被过度判定为“已反驳”。一个错误置信度为 0.92，不能自动采信。保留默认 OFF，试用采用显式 SHADOW；不自动放行，不影响两次 Worker 限制。

原计划的两组独立 Astra API 审核没有完成：基线请求两次失败，第二次确认 HTTP 402，余额不足以支持 max_tokens=1800（接口报告最多可负担 799）。第一次记录缺少错误正文，不能独立断言其具体 HTTP 状态。没有第三次重试、改名重跑、充值或转用另一个模型绕过次数。实验组的 Astra 调用未发起。

随后由当前 Commander 直接检查源码、固定标签和 Jev 输出。因此现在具备“代码基线 vs Jev 筛查”的小型探针结果，不具备两个独立强模型流程的统计性成本或速度比较。不能称为已证明更优。

## 实验设计与证据

- 在任何模型返回前冻结 packet.json 与 gold.json。
- 18 条、三类各 6 条；6 条代码支持的陈述，12 条人工植入的反事实或无证据声明。负例不是项目真实缺陷。
- 材料来自本仓库代码/公开说明的 9 组摘录，存在共用证据，18 项不是18个独立生产任务。
- 只把 packet（claim + evidence）发送给 Jev；gold、标签理由不发送。
- 同一 Commander 构造标签并审查结果，非盲法独立人工标注；小样本、选择偏差和中文领域局限明确保留。
- 计划无 Jev：Astra low 审核全部条目。计划有 Jev：相同 Astra、原始材料、验收条件，加 Jev 提示，仍须逐项审核。禁止通过跳过安全审核来制造节约。
- run_comparison.py 保留可重现实验入口，但重新运行收费实验属于新的明确实验计划；现有失败输出不能覆盖或伪装成成功。
