# 外部执行工作者契约

本契约定义策略对 `codex-worker` 的最小接口和行为期望。仓库不包含该程序的实现，也不指定供应商、模型或网络端点。

## 权限与职责

协作链的最高权力属于人类。人类设定目标、预算和约束，保留最终接受、拒绝与推翻任何结果的权力。当前主会话承担指挥者职责，在人类授权内定义任务，作出架构与委派决定，审查关键证据并完成风险相称的技术验收；该职责不绑定特定模型或供应商，能力不足时必须披露并升级。工作者只执行范围明确的任务、生成制品和提交证据。

人类监督不等于每一步都要重新批准。已经明确授予且尚未撤销的权限持续有效，指挥者和工作者可以在其边界内推进正常步骤；超出预算、范围或外部影响边界，遇到保留决定，或者证据不足时，才应升级。人类可以随时收窄或撤销授权并调整或否决结果。

## 命令接口

用户自行提供的可执行程序必须位于 `PATH`，并满足：

```text
codex-worker <workspace>
```

- 第一个位置参数是工作区路径。
- 完整任务提示从标准输入读取。
- 人类可读的最终报告写到标准输出。
- 诊断信息可写到标准错误。
- 成功执行接口时返回 `0`，执行失败返回非零状态；退出码只描述进程结果，不代表指挥者技术验收。

先执行：

```sh
command -v codex-worker >/dev/null 2>&1 || {
  echo "codex-worker is required but was not found on PATH" >&2
  exit 1
}
```

最小调用：

```sh
cat <<'WORKER_PROMPT' | codex-worker "$PWD"
MODE:
DOCUMENT

TASK ID / ATTEMPT:
[稳定任务 ID] / [1 或 2]

OBJECTIVE:
生成一个范围受限、可验证的本地文档交付物。

TASK:
读取必要材料，完成编辑，自检链接和事实一致性。

REQUIREMENTS:
- 不读取工作区外材料。
- 不执行外部发布。
- 不虚构检查结果。

ACCEPTANCE CRITERIA:
- 指定文件存在且内容完整。
- 实际执行的检查及结果被准确报告。

AUTONOMY:
执行合理的 inspect -> execute -> verify -> fix -> reverify 循环。

OUTPUT:
使用约定报告结构，列出风险与未决判断。
WORKER_PROMPT
```

## 输入契约

一份可执行提示应包含：

- `MODE`：领域模式。
- `TASK ID / ATTEMPT`：同一逻辑任务的稳定标识与当前 Worker 轮次。
- `OBJECTIVE`：最终业务或工程结果。
- `CONTEXT`：仅限必要背景，不倾倒无关材料。
- `TASK`：本次执行的准确范围。
- `REQUIREMENTS`：必须保持、禁止和约束条件。
- `ACCEPTANCE CRITERIA`：可观察、可验证的完成条件。
- `AUTONOMY`：允许的修正和重试循环。
- `OUTPUT`：报告结构和证据要求。

派发前还必须记录允许范围、当前基线和相关已验证项目经验。任务 ID 不因换 Worker、模型、会话、名称或目标版本而重置；真实独立的新范围要记录理由和谱系。

使用[委派模板](../templates/delegation.md)可以减少遗漏。提示不得包含凭据、令牌、无关个人数据或未获准对外处理的材料。

## 行为契约

工作者应先检查上下文，再执行范围内工作；保持无关行为和内容；在本轮明确停止条件内对普通失败自行诊断、修正和重新验证；区分事实、推断和不确定性；报告所有实际改动与检查；在权限、依赖或关键决策阻塞时停止扩大范围。内部自检不另算轮次，但不能无休止循环。

同一逻辑任务最多启动两次 Worker：初次执行和一次指挥者要求的修正。启动即计数；中断或状态不确定时保守计数；等待同一运行中的进程不计新轮次。第二次仍未满足验收条件，指挥者必须接管修复、测试和复核，也可以更早接管。基础设施失败不能重置次数。

工作者不得自行作出高风险架构、认证、授权、安全或数据库策略决定，不得决定论文最终创新主张或现实世界建议。除非任务明确授权相应行为，否则不得提交、推送、发布、发送消息或改变外部系统。

以下事项始终不应交给工作者：检查 API 密钥、修改凭据、修改认证、修改 Codex 配置、修改私有工作者配置目录、递归启动另一个工作者或继续委派编排。凭据只能由人类或指挥者变更；不得把凭据放入任务提示、报告或仓库文档。

## 输出契约

报告应紧凑但可审计，使用[工作者报告模板](../templates/worker-report.md)，至少包含：执行摘要、发现、完成工作、重要证据、文件或章节、实际检查、风险、不确定性、未作决定、需要指挥者判断的事项和下一步建议。

报告应包含任务 ID、当前轮次、实际证据和建议写入经验记录的事实。报告中的验证必须使用完成时态且可追溯。例如“运行 `npm test`，退出码为 0”是证据；“测试应该会通过”不是。无法运行时，应陈述原因和仍缺少什么，而不是推断通过。

每次提交后由指挥者记录证据、缺陷与 `accept / rework / takeover / blocked` 决定。必要检查未运行时只能阻塞，不能接受；Worker 自报、退出码 `0` 或 `APPROVE` 文本不构成技术验收。最终交付还要求当前制品与项目本地经验记录均通过指挥者检查，人类最终接受仍然独立。

## 可替换性：角色、模型与适配器

“工作者”是协作角色，不等同于某个模型或供应商；“模型”负责推理与生成；“适配器”才是把具体 API、命令行工具或本地推理后端接入本契约的实现。稳定边界是：同一授权工作区、通过标准输入提交的任务、标准输出报告与工作区制品，以及可检查的进程退出状态。

| 层次 | 可替换内容 | 必须保持的约束 |
| --- | --- | --- |
| 角色 | 有界执行者的职责分配 | 不取得人类或指挥者的决策权 |
| 模型 | 供应商、模型或版本 | 达到相同任务的验收标准 |
| 适配器 | API、CLI 或本地运行接线 | 正确实现工作区、标准输入、报告/制品和退出状态契约 |

API 服务与本地模型只是概念上的候选后端；没有实际工具集成和经过审查的适配器，它们不会自动满足 `codex-worker` 接口。本仓库不声称支持所有模型，也不承诺模型可以热切换。

更换供应商、模型、版本或重要配置前，应在相同代表性任务上做试运行，并保持范围和验收标准一致。至少核对：指令遵循、工具调用及权限行为、证据准确性、交付质量、延迟和实际总成本。更换后端不重置未解决任务的两轮额度。试运行通过后仍由指挥者完成技术验收，人类保留最终接受或调整或否决权。可用[成本与质量复核模板](../templates/cost-review.md)记录结果；一次成功不代表对其他任务普遍兼容。

## 手动后备

若 `codex-worker` 不存在或不兼容，不要下载未知程序、自动信任任意目录或临时创建未经审查的运行适配器。可在干净的专用工作区人工准备同一提示，删除敏感和无关内容，将其交给用户自行选择的执行系统，然后按本契约人工检查返回文件和证据。

该契约只定义协作预期，不是沙箱。实际文件访问、网络、数据保留和模型训练边界由工作者实现及第三方提供方决定。
