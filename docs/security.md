# 安全与授权边界

本项目提供的是提示和审查政策，不是沙箱、访问控制器、数据防泄漏系统或供应商合规证明。文字指令无法替代操作系统权限、容器隔离、网络策略、密钥管理和人工审查。

人类处于权限链顶端，决定目标、预算、约束并拥有最终接受、拒绝和调整或否决权。当前主会话作为指挥者，在人类授权内定义任务，作架构与委派决定，审查关键证据并作技术验收；能力不足时必须披露并升级，不能假装已经切换模型。工作者只有完成指定范围工作的权限。已有授权持续有效，人工监督不要求每一步重复审批，但任何越过授权边界的动作都必须升级。

## 数据会去哪里

外部工作者使用第三方提供方时，你提交的提示、粘贴的内容以及工具能够访问的材料可能离开本机，并受该提供方的数据保留、日志、训练、地域、人员访问和删除政策约束。使用前应了解这些条款，逐项检查出站内容，并只提交完成任务所需的最小材料。

不要把凭据、令牌、私钥、未公开客户资料、受限制数据或无关个人信息放入提示。`.gitignore` 不是安全边界，文件未被 Git 跟踪也不代表工作者无法读取。

## 工作区卫生

- 优先使用干净、专用、可回滚的工作区，并授予最小文件和网络权限。
- 运行前确认解析后的工作区路径和预期文件范围，不要自动信任任意目录。
- 先查看项目现有指令。若已有 `AGENTS.md`，比较、审查并合并政策；不要直接覆盖。
- 不要把本政策默认写入用户级或全局代理配置，以免意外影响其他项目。
- 审查提示和附件，移除不必要的源码、日志、元数据和身份信息。
- 对生成的命令、补丁和外部引用进行人工检查后再接受。

## 明确禁止委派

不要要求工作者：

- 检查 API 密钥或其他凭据；
- 修改凭据或认证机制；凭据只能由人类或指挥者变更；
- 修改 Codex 配置；
- 修改私有工作者配置目录；
- 递归启动另一个工作者；
- 将编排任务再次委派；
- 通过扩大权限绕过失败；
- 在没有相应授权时执行外部发布或通信。

认证、授权、安全策略、数据访问策略及其他高风险技术决定由指挥者保留，人类仍拥有最终接受与调整或否决权。除上述禁止委派事项外，工作者可以在明确决策之后实施受限变更，但必须接受深入复核。

## 本地接受与外部授权

以下是两个不同的状态：

1. **本地工作已接受**：指挥者确认工作区中的改动满足要求。
2. **外部行为已授权**：用户允许对应的推送、拉取请求、发布、消息发送、公开仓库或其他外部状态变化；已有授权持续有效，无需重复确认。

第一个状态不自动产生第二个状态。反过来，任务已明确授权的普通本地实施步骤不需要重复逐步审批。应按行为范围判断授权，而不是建立笼统的“每一步都问”规则。

## 输出与证据审查

外部工作者的报告是不受信任的输入。检查其中的文件路径、命令、退出状态、测试范围和未决风险。退出码 `0`、自报完成或 `APPROVE` 文本都不是技术验收。高风险任务应直接核对实现和原始证据；中风险任务检查关键路径和代表性样本；低风险任务仍需确认自动检查确实运行。必要检查未运行时只能标记阻塞，不能接受。

不要接受以下表述作为完成证据：“应该通过”“看起来正确”“预计没有影响”或没有来源的性能数字。未运行的测试必须明确标记。示例、模板和假设数据必须标记为说明性材料，不得冒充实际基准、用户历史或生产结果。每个委派任务的项目经验记录也要排除凭据、个人偏好、私有配置和无关专有内容；经验是有范围的证据，不是新权限。

同一逻辑任务最多两次 Worker 执行。更换 Worker、模型、会话、名称或目标版本不重置同一未解决工作的次数，也不能作为绕过权限或复核的手段；第二次失败后由指挥者接管并检查自己的修复。真实独立的新范围必须记录理由和谱系。

## 事故与异常

若发现敏感材料可能被提交给第三方，停止继续发送内容，保留最少必要的本地事实记录，并按组织既有的安全与供应商响应流程处理。不要让工作者自行检查密钥或修改认证来“修复”事件。

若命令解析到意外路径、要求超出范围的权限、尝试访问私有配置或递归启动工作者，应终止执行，检查实现和调用参数。安全边界不明确时，回到手动、最小范围的流程。
