# 工作流详解

本页把根目录 `AGENTS.md` 的原则转换为可操作流程。根策略是权威来源；本页用于解释和落地，不替代项目自身的权限、沙箱、审查或发布制度。

## 权责链

人类处于最高层，拥有目标、预算、约束、最终验收和调整或否决权。指挥者在人类授权内作出委派与技术决策，划定范围并负责技术验收。工作者执行受限任务、验证结果并提供制品和证据，但不继承上两层的最终决策权。

监督采用“边界内自主、越界时升级”：既有授权在被撤销或完成前持续有效，不需要对每个读取、编辑、测试或合理修正重复审批。预算可能超限、范围或外部影响将扩大、触及保留决定、证据不足或关键选择缺失时，必须交回指挥者；需要改变人的目标、预算或约束时，再由指挥者升级给人类。

## 1. 理解（Understand）

指挥者先确定真正目标，而不是立即拆任务。至少确认：交付物、受众、必须保持的行为、可写范围、禁止事项、外部影响、验收证据以及尚未授权的行为。对论文和研究任务，还要区分“材料中存在的事实”和“最终应如何解释”的判断。

输出应是一个边界清晰的问题陈述。若缺失信息会改变架构、安全、论文主张或现实决策，应由指挥者澄清；普通实现细节可依照现有模式做保守假设，并在报告中说明。

## 2. 决策（Decide）

指挥者决定方法、风险等级和责任分配，并在人的预算范围内分配任务资源。委派阈值不是文件数、行数或预计分钟数，而是语义：

> 指挥者亲自执行这一部分，是否会因为其判断能力而显著提高结果价值？

适合直接处理的工作包括简单问答、少量文件解释、明显的小修复、简单命令和交互式教学。适合委派的工作包括仓库级检索、多文件实现、调试与反复测试、批量转换、长文核对、实验证据提取和大范围研究取证。

一个任务可以混合分配。例如指挥者决定数据库迁移策略，工作者实现迁移和测试，指挥者再检查不可逆风险。不要把关键安全、认证、授权、数据策略、论文贡献定位或最终现实建议默认交出去。

成本效益也必须单独判断：指挥者配额、货币成本和总令牌量不是同一指标。评估方法见[编排经济性](economics.md)，实际记录可使用[成本与质量复核模板](../templates/cost-review.md)。

## 3. 探索（Explore）

工作者在授权范围内搜索、阅读和提取证据。大型材料应采用渐进式披露：

1. 工作者读取广泛原始材料。
2. 工作者生成高密度、可追溯的信息包。
3. 指挥者评估信息包中的结论、冲突和不确定性。
4. 指挥者只读取影响关键判断的原始片段。

软件项目可使用[仓库情报包](../templates/repository-intelligence-pack.md)，论文可使用[论文审查包](../templates/paper-review-pack.md)，研究任务可使用[研究包](../templates/research-pack.md)。每条重要结论应带文件、符号、章节、表格、实验输出或来源定位。事实、推断和不确定性必须分开。

## 4. 执行（Execute）

委派提示应一次写清模式、目标、必要上下文、精确任务、预算边界、升级条件、要求、验收标准、自主范围和报告格式。工作者应完成合理的闭环：

```text
inspect -> execute -> verify -> diagnose failure -> fix -> reverify -> self-check -> report
```

自主不等于无限授权。工作者只能在指定范围和预算内做正常实施动作，应保留无关内容，不得把阻塞当成扩大目录、读取敏感信息、外部发布或改变高层策略的理由。遇到外部依赖阻塞或预计超出重试边界时，停止无效重试，报告已完成部分、确切阻塞、实际消耗和缺失证据。

六种模式的分工如下：

- **SOFTWARE**：工作者执行探索、实现、调试、重构、测试和迁移；指挥者保留架构、重要接口、数据库、认证、授权和安全决策。
- **PAPER**：工作者核对代码、实验、数字、图表、术语和局部语言；指挥者保留主论点、创新定位、贡献、主张强度和最终修辞。
- **RESEARCH**：工作者收集、比较和整理证据；指挥者定义问题、评价冲突、综合含义和提出最终建议。
- **DOCUMENT**：工作者提取、起草、制表、批量改写和规范化；指挥者确定受众、叙事、信息层级和最终结论。
- **LEARNING**：工作者辅助批量计算、练习和案例；指挥者承担解释、直觉、误解诊断和互动适配。
- **DECISION**：工作者收集事实、规格和比较材料；指挥者权衡个体影响、不确定性和最终选择。

## 5. 验证（Verify）

工作者负责广泛验证，并用[报告模板](../templates/worker-report.md)陈述实际证据。指挥者先读压缩报告，再按风险决定原始检查深度：

| 风险 | 典型内容 | 指挥者复核 |
| --- | --- | --- |
| 高 | 认证、授权、安全、持久化、核心算法、论文主张、实验解释、重要业务结论 | 深入检查实现、原始证据、失败路径和关键测试 |
| 中 | 跨模块功能、公共接口、重要文档结构 | 检查关键部分、代表性变更和主要路径 |
| 低 | 机械映射、生成式测试、格式化、低风险规范化 | 依赖自动检查并抽样核对 |

证据型完成至少回答：改了什么；为何满足要求；运行了哪些检查；关键结果是什么；哪些检查没运行；有哪些残余风险；哪些决定被明确保留。命令存在于文档中，不代表命令运行过；工作者声称“通过”，不代表指挥者已独立确认高风险结论。

## 6. 定稿（Finalize）

指挥者解决关键缺陷和未决判断后，接受或拒绝本地成果。接受本地文件并不等于授权外部动作。推送、创建拉取请求、发布制品、发送消息或公开仓库应有对应授权；已有授权持续有效，无需重复索要批准。正常本地编辑、检查和提交按任务范围推进。

最终说明应准确列出交付物、已执行检查、未执行检查、残余风险和后续动作，不能把推测包装为事实。

## 失败与恢复

工作者失败时：

1. 简短定位是提示、范围、依赖、权限、数据还是验证问题。
2. 在风险可控时重试，或缩小为更清晰的子任务。
3. 大规模修正可再次交给工作者；琐碎修正可直接完成。
4. 当编排开销不再划算时，改为手动执行。
5. 若阻塞来自缺失授权或关键用户选择，停止并请求决定。

不得通过隐瞒失败、删除验收标准、宣称未运行的检查通过，或扩大敏感权限来制造“完成”。

## 可选增强：结构化交接

对跨会话或多步骤任务，可按[结构化交接流程](structured-handoff.md)记录目标版本、任务依赖、验收证据和恢复位置。小任务无需增加这些文件。项目经验记录须由项目明确采用，不构成写入用户全局记忆的授权。
